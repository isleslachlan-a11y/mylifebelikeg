# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A life-planning web app for setting goals, planning trips, and tracking progress against budgets and timelines. Individual-first: every object is owned by one person, and sharing is an explicit grant on top. Designed to scale beyond two users to public signup. Commit history is phase-numbered: `P0.x` = pre-launch scaffolding (auth, shell, design tokens, Supabase clients — done). `P1.x` = goals (life areas, goal CRUD/lifecycle, participants, milestones, tasks, schedule variance, per-goal mini timeline — done). `P2.x` = money (current phase — pots, cashflow items, FX rates, the ledger, pledges/allocation, budget variance, and the money dashboard at `/money` are built). Trips, check-in, and the full cross-goal timeline are still unbuilt stub pages; the latter's requirements are pre-specified in `PHASE-3-REQUIREMENTS.MD` (see Architecture).

## Stack

Next.js 16 (App Router) + TypeScript, Supabase (Postgres + Auth + RLS), Tailwind CSS v4, shadcn/ui (`radix-nova` style), deployed on Vercel.

## Commands

```bash
npm run dev          # start dev server
npm run build         # production build (also run by CI)
npm run lint          # eslint
npm run format         # prettier --write .
npx tsc --noEmit       # type check (CI runs this after `next typegen`, see below)
npm test               # vitest run — unit tests
npm run test:watch     # vitest watch mode
npm run db:types       # regenerate src/types/database.ts from the live schema; requires SUPABASE_PROJECT_ID
```

Unit tests (Vitest) are colocated as `*.test.ts` next to the module they cover (e.g. `src/lib/money.test.ts`, `src/lib/timeline/scale.test.ts`, `src/app/(app)/goals/goal-transitions.test.ts`) — run a single file with `npx vitest run path/to/file.test.ts`. `vitest.config.mts` runs everything under `environment: "node"`: pure-logic tests only, no React component tests yet (no `jsdom`/`@testing-library/react` installed — add them per the Next.js Vitest guide in `node_modules/next/dist/docs/` if/when component tests show up). **`npm test` is not yet part of CI** — don't assume a green PR means tests were run; run it yourself. Correctness for SQL (schema, triggers, RLS) is checked separately by running the `supabase/local/*` scripts against a scratch Postgres — see "Database" below. There's also no Storybook; UI states meant for visual review live at `/styleguide` and `/styleguide/llamas` (real routes in the running app, not a separate tool).

CI (`.github/workflows/ci.yml`, runs on every PR) does, in order: `npx next typegen` (needed so `tsc` can see route-generated types like `LayoutProps`/`PageProps`), `tsc --noEmit`, `npm run lint`, `npm run build`. It's a gate only — Vercel's own GitHub integration builds and deploys independently of it, so CI passing/failing doesn't control whether a deploy happens.

To run a single non-test check rather than the whole CI sequence, run that one command above directly — there's no per-file filtering for lint/build.

## Non-negotiable rules

1. All monetary values are integers in minor units (cents/pence) with an explicit 3-letter currency code alongside. Never floats, never a bare number. Format for display only at the render boundary.
2. Never query Supabase from client components with the service role key. All privileged operations go through Next.js route handlers or server actions.
3. Row Level Security is the security boundary. Never disable it, never bypass it with the service role to "make a query work". If a query returns nothing, the policy is the thing to inspect.
4. Dates are stored UTC (`timestamptz`) or as a bare `date` where time of day is meaningless. Display in the user's timezone from `profiles.timezone`.
5. Task dates are derived from `offset_days` + `duration_days`, never entered directly.
6. Database types are generated from the schema, never hand-written. Regenerate after any migration.
7. No `localStorage` or `sessionStorage` for application data.

## Architecture

**Route groups.** `src/app/(auth)/` (login, signup, onboarding — reachable while unauthenticated) and `src/app/(app)/` (dashboard, timeline, goals, trips, money, check-in, profile — gated). The split is enforced in code, not just by folder naming: `src/lib/supabase/middleware.ts` (invoked from `src/proxy.ts`, see Gotchas) redirects based on auth state and whether a `profiles` row exists yet, using explicit `AUTH_ROUTES`/`UNGATED_ROUTES` allow-lists rather than inferring from the route group.

**Three Supabase client constructors, not one** — pick the one matching where the code runs, don't share instances across requests:

- `src/lib/supabase/client.ts` — browser/Client Components, anon key.
- `src/lib/supabase/server.ts` — Server Components/route handlers/Server Actions, cookie-based session, created fresh per request.
- `src/lib/supabase/middleware.ts` — the proxy/middleware layer specifically; the one place session-cookie writes are guaranteed to succeed (Server Components can't write cookies at all — `server.ts`'s `setAll` silently no-ops there by design).

**Server action conventions** (`src/app/(app)/goals/`, mirrored under `src/app/(app)/money/`). Goal, task, milestone, and participant mutations each live in their own `"use server"` file (`actions.ts`, `[id]/tasks-actions.ts`, `[id]/milestones-actions.ts`, `[id]/participants-actions.ts`); money's pots, cashflow, FX, and ledger each get their own `actions.ts` the same way. All of them share a `ActionResult<T> = { ok: true; data: T } | { ok: false; error: string }` return shape rather than throwing. Two things repeat across all of them, deliberately:

- A local `getUserId(supabase)` helper calls `auth.getClaims()` and `redirect("/login")` on a missing session — every action runs from an already-gated `(app)` route, so a missing session here means it expired mid-use, not a first visit.
- Whether an extra `owner_id`/`goal_id` filter gets layered on top of a query is a conscious per-table decision, documented inline at each `getUserId`: it's added where RLS alone is broader than what the UI should allow, and skipped where the RLS policy (e.g. `tasks_write`/`milestones_write` as `app.can_edit_goal(goal_id)`) already is the exact authorization surface wanted. Don't add a filter "for safety" without checking which case applies — an unnecessary one can silently exclude collaborator-owned rows.

The goal lifecycle graph itself lives in `[goals/]goal-transitions.ts`, split out from `actions.ts` purely because a `"use server"` file may only export async functions — `ALLOWED_GOAL_TRANSITIONS` and `transitionLabel` need to be imported as plain values by both the server action and client-rendered buttons. Follow the same split for any future enum-driven state machine (task/milestone status, trip status, etc.).

**The llama message system** (`src/lib/llamas/`) is the app's copy/notification layer: two personas, Derek (blunt, handles red/amber/overdue) and Fluffy (warm, handles green/completions/streaks). `types.ts` defines the `TriggerCode` union and per-trigger params; `registry.ts` maps each trigger to a speaker + priority (the speaker is decided once, centrally — call sites never pick a llama); `copy.ts` holds enumerable copy variants per trigger, viewable side-by-side at `/styleguide/llamas`. Adding a new triggered message means touching all three files. Wiring these triggers to real app events hasn't happened yet — `copy.ts`'s `getLlamaCopy` is what real call sites will eventually use.

**Money's dashboard is view-heavy, not computed in application code.** `/money` (`src/app/(app)/money/page.tsx`) and its sub-pages read from Postgres views — `v_allocation_summary`, `v_pot_balances`, `v_goal_funding`, `v_goal_affordability` — rather than joining and aggregating client-side; `src/lib/budget-variance.ts` and `src/lib/money.ts` only handle the pure display-side math (variance calc, minor-units formatting). If a money number looks wrong, check the view definition (`Schema.MD` / the migration) before suspecting the TypeScript. `v_goal_affordability` covers `save_toward` goals only — `spend_against` goals don't have an affordable-from date, per `006 affordability test`.

**Database.** `Schema.MD` is the narrative source of truth for the data model (24 tables, RLS design, RAG scoring rules, FX handling, what's built vs. not-yet-wired) — read it before touching anything schema-adjacent, it explains _why_ the shape is what it is, not just what it is. `supabase/migrations/` is still catching up to the live schema: as of this writing it holds `0009_monthly_cashflow_breakdown.sql`, `0011_timeline_items_view.sql`, and `0012_financial_horizon.sql`, not the full history the live Supabase project was built from — don't assume the directory is a complete, replayable log, and don't assume its numbering is gapless (`0010` is deliberately unclaimed here — see PHASE-3-REQUIREMENTS.MD's R2 — so check the live schema/`database.ts` rather than the highest committed filename when picking the next number). `src/types/database.ts` is already generated against the real schema (regenerated and reformatted after 0012, confirmed against a real `supabase gen types` run, not hand-written — rule 6 intact), so trust that file for current table/column shapes even where migration SQL is absent. Worth remembering regardless: this session had a near-miss where an uncommitted regen (added after 0011, never committed) got silently reverted by an unrelated `git checkout` used to undo a *different* failed regen attempt — everything from P3.1 onward ran on that uncommitted file without anyone noticing until a later `tsc` run broke. **Commit `database.ts` in the same change as the migration that required it**, not later; an uncommitted regenerate-after-migration is one `git checkout` away from silently reverting to the last committed schema shape. `supabase/local/*` are numbered psql scripts (`000 auth shim` through `006 affordability test` — auth shim, smoke test, RLS isolation test, schedule test, life areas test, timezone test, affordability test) for validating schema changes against a throwaway local Postgres before they touch the real project — see the "Running it locally" section of `Schema.MD` for the exact sequence.

**Timeline math (`src/lib/timeline/`).** `scale.ts` wraps `d3-scale`'s `scaleTime` into an orientation-agnostic `TimelineScale` (`toPixel`/`toPixelSpan`/`ticks`) that only ever returns numbers — it has no opinion on `left`/`width` vs. `top`/`height`, or on layout at all. P3.0 extended it with a second, zoom-aware constructor, `createScale(zoom, anchorDate, rangePx)`: the domain is derived from `ZoomLevel` (day/week/month/quarter/year) and centred on `anchorDate` rather than fit to a data extent — at day zoom a multi-year extent is unrenderable. `widthForItem` is a thin, duck-typed wrapper (`{ toPixel(date): number }`) shared by both scale shapes, so call sites reach for rendered pixel width instead of branching on `duration_days` (R1). `stack.ts` (P1.11) does interval-stacking for the per-goal mini timeline; `stacking.ts` (P3.2) is the full-timeline sibling — same "minimum meeting rooms" greedy idea but a distinct implementation, not a shared one, because its placement order is `starts_on`/`sort_order`/`item_id` (a calendar-date sort, per R4), a different axis from `stack.ts`'s sort-by-pixel-start. Its `assignSubRows` folds each item's estimated label width into its effective pixel footprint (labels collide before bars do), reserves a single sub-row for milestones (never stacked among themselves, never interleaved with bars), and excludes goals entirely (they're a background band, not a competing bar — rendered separately in P3.4's `HorizontalTimeline`). `lanes.ts` (P3.3) splits a set of items into life-area/owner/goal lanes — also `Date`-free (bare ISO date strings sort correctly as strings, so there's no reason to touch `Date` until a lane's items reach `assignSubRows`). `item-status.ts` (P3.4) derives a four-way completed/overdue/in_progress/not_started classification from `is_complete` + dates + a caller-supplied `today` — deliberately *not* from `tasks.status`'s richer enum, which isn't available this far down (`v_timeline_items.status` is the parent goal's state, not each item's own — see 0011's migration); this follows `goal-timeline.tsx`'s existing precedent of deciding "overdue" from dates rather than the enum. `overlays.ts` (P3.6) is the last pure piece, and genuinely shared *rendering-adjacent* logic rather than layout: `computeOverlayLine` positions a single-point-in-time guideline (today marker, financial horizon) against any scale, and `needsStickyLabel`/`needsTruncatedLabel` encode R1's width-vs-viewport decision — both orientations call the same functions, just feeding them width or height depending which axis time runs on there. All of this is shared between P1.11's per-goal mini timeline (`src/components/timeline/goal-timeline.tsx`) and the full cross-goal timeline (Phase 3, in progress) — keep layout/component concerns out of this directory; it stays plain-`Date`-(or bare-date-string)-in/numbers-or-lanes-out. `PHASE-3-REQUIREMENTS.MD` (binding, derived from a since-deleted spike whose findings are preserved in `SPIKE-NOTES.md`) specifies the constraints that timeline work must satisfy: sticky labels keyed off rendered pixel width not duration, a single timezone-derived `today` computed once per request, bars anchored at their start (not centered), pixel-space (not date-space) collision stacking, range-windowed queries rather than list virtualization, and shared scale/separate-per-orientation layout constants. Read it before touching anything under `timeline/`.

**Horizontal timeline layout (`src/components/timeline/horizontal-timeline.tsx`, P3.4/P3.6, desktop/≥768px).** One `overflow-auto` container, `position: sticky` doing the pinning independently per axis (`top` for the date axis row, `left` for the lane-label gutter column, both for the corner cell) — not multiple scroll containers with JS-mirrored `scrollLeft`/`scrollTop`. Nothing between the sticky elements and that single scrolling ancestor may carry `overflow-hidden`/`overflow-clip` (R1) — that's the literal bug that broke the P0.8 spike's band labels on scroll, so it's worth checking first if a sticky element here ever stops sticking. Bars anchor at `starts_on` and are never centred (R3); milestones are the one deliberate exception, centred on their date as diamonds. Owns its own layout constants (gutter width, bar height, axis height, lane padding) — deliberately not exported and not shared with `vertical-timeline.tsx`. P3.6 added the today-marker/financial-horizon overlay (`OverlayLines`, spanning every lane via CSS Grid's `grid-row: 1 / -1` rather than computing total content height in JS) and per-item labels (`ItemLabel`): `position: sticky` is applied to a bar/band's label unconditionally, since it's inert until the item is actually wider than the viewport — the `needsStickyLabel` decision only gates a cosmetic backdrop chip, not correctness, which matters because there's no real viewport measurement wired up here (`ASSUMED_VIEWPORT_PX` is a documented guess, not a `ResizeObserver` reading).

**Vertical timeline layout (`src/components/timeline/vertical-timeline.tsx`, P3.5/P3.6, mobile/<768px).** A second, separate component — no `orientation` prop threaded through the horizontal one, per R6 and both packages' briefs. Same single-`overflow-auto`-plus-sticky-children structure as the horizontal layout, but transposed: time runs top to bottom, the date axis is a fixed-`left` rail (not a fixed-`top` row), and lanes stack as vertical collapsible sections instead of horizontal rows — `TimelineView`'s existing mobile single-expand state (P3.3) drives which one lane is open. The genuinely interesting bit is what carries over from `assignSubRows` unchanged: its sub-row numbers become *horizontal* offsets here (an overlapping item sits to its right, not below it), so it's lane *width*, not height, that depth drives — the exact same function, reinterpreted onto the other axis, which is what R6 means by "the date maths transfers cleanly but the layout constants do not." Own layout constants again (rail width, column width, column gap) — not shared with `horizontal-timeline.tsx`, and the 4-way status-colour mapping is independently re-declared here too rather than imported, same colocation reasoning as `goal-timeline.tsx`'s `taskFill`/`milestoneFill`. `TimelineView` now owns zoom *and* pan itself (it didn't before P3.5) specifically so it can default zoom to week on mobile / month on desktop and keep tracking that default — for as long as the user hasn't picked a zoom manually — as the breakpoint changes. P3.6's overlay lines run *horizontally* here (`top: px`) instead of vertically, and only ever render inside whichever one lane is expanded — with only one lane's body ever in the DOM on mobile, "across all lanes" already means "within the expanded one." P3.7's `onHoverItem`/`onNavigate` split (hover/focus previews, click navigates to `/goals/[id]`) is identical in both orientation components — an interaction-semantics decision, not layout, so it isn't something R6 says to keep separate.

**Navigation and interaction (P3.7).** `TimelineView` now also owns hover/focus state (`hoveredItemId`, repurposed from what used to be click-selection — click navigates now, per the brief's explicit "no drag, no resize, no inline editing here; editing happens on the goal detail page"), a `useRouter().push("/goals/[id]")` navigate handler, and a keyboard-shortcut effect (`+`/`=`/`-`, guarded against firing while an input/textarea/select/contenteditable has focus). Zoom never touches `anchor` — only `zoom` — so "zooming preserves the centre date" holds by construction, not by any special-cased recovery logic; `scale.test.ts` has a dedicated test for exactly the year-to-day case P3.7's acceptance criterion names. The hover card (`item-hover-card.tsx`) renders as a fixed corner panel keyed off `hoveredItemId`, not a cursor-following tooltip — schedule variance on it is optional and caller-supplied (`scheduleVariances` prop, a `Map<goalId, pp>`) for the same reason `ownerNames`/`goalTitles` already are: `v_timeline_items` doesn't carry what `computeScheduleVariance` needs. The two empty states are told apart by a second, unwindowed existence check (`hasAnyGoalsEver`, a one-off `goals` count query, deliberately separate from the windowed/filtered hook) — `displayItems.length === 0` alone can't distinguish "no data" from "filtered/windowed to nothing."

**Timeline lane components (`src/components/timeline/`, P3.3).** `TimelineView` is the stateful container the brief calls for — grouping mode, filters, per-lane collapse state, and selection all live here as plain `useState`, never `localStorage`. Desktop and mobile collapse state are two *separate* pieces of state (`desktopCollapsedLaneIds` vs. a single `mobileExpandedLaneId`), not one derived from the other — that's deliberate: switching to mobile never touches the desktop set, so switching back restores it untouched, which is what makes surviving the breakpoint switch (R6) true without extra bookkeeping. `TimelineLanes` underneath is purely presentational (given `Lane[]`, render them); neither component is ever remounted or `key`ed by grouping mode or breakpoint, since that's exactly what would reset scroll position. `timeline-item-adapter.ts` bridges `v_timeline_items`'s all-nullable generated row type (Postgres reports every view column nullable, regardless of the underlying tables' real constraints) into the non-null shapes `lanes.ts`/`stacking.ts` expect, dropping any row missing a required field rather than crashing. `useIsMobile` (`src/hooks/use-is-mobile.ts`) is `useSyncExternalStore` used the way the P0.8 spike notes say it should have been the first time (R2) — subscribed to `matchMedia`'s actually-stable `matches` value, not a continuously-changing clock, with a fixed `false` server snapshot to avoid a hydration mismatch. One non-obvious data fact worth knowing before touching life-area grouping: "Uncategorised" is a real, system-seeded `life_areas` row (`is_system: true`, own `id`/`colour`/`sort_order`) that `goal-form.tsx` already defaults every goal into — not a `null`-`life_area_id` sentinel. `lanes.ts` still handles a genuinely null/unmatched `life_area_id` (a synthetic fallback lane, shown only when it has items), but that path is a defensive edge case, not the common one.

**Timeline data layer (`src/hooks/use-timeline-items.ts`, P3.1).** The first (and so far only) client-side Supabase query in the app — everything else goes through server actions/server components, but a scroll-driven data layer has to live on the client. Queries `v_timeline_items` (0011's view — unions goals/milestones/tasks; `status` on every row is the *parent goal's* state, not each item's own, specifically so "active goals only" filters uniformly across item types; each item's own completion is `is_complete` instead) windowed to the visible range plus a ~1-viewport buffer (R5), debounced ~150ms, and cached by (filters, buffered window) so scrolling back to an already-fetched window is a cache hit. `src/app/(app)/timeline/debug-items/` is a dev-only (`notFound()` in production) harness that dumps its output as JSON — same convention as `/styleguide`, but inside `(app)` because it needs a real session for RLS. This is data-fetching only; no rendering built on it yet.

**Deployment** is documented in `DEPLOYMENT.md`: no `vercel.json` (defaults are correct), the three required env vars and why `SUPABASE_SERVICE_ROLE_KEY` must never gain a `NEXT_PUBLIC_` prefix, Supabase Auth redirect allow-list config, and the migration-then-regenerate-types workflow.

## Gotchas

- This Next.js version deprecated `middleware.ts` in favor of `src/proxy.ts` (exported function named `proxy`, not `middleware`). A `middleware.ts` file is silently never invoked — no build error, no warning in dev output beyond an easy-to-miss deprecation notice — and because it's also at the project root rather than `src/` (this project uses `src/app`), a root-level `proxy.ts` is _also_ silently never invoked. Confirm it's live by checking `next build` output for a `ƒ Proxy (Middleware)` line.
