# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A life-planning web app for setting goals, planning trips, and tracking progress against budgets and timelines. Individual-first: every object is owned by one person, and sharing is an explicit grant on top. Designed to scale beyond two users to public signup. Commit history is phase-numbered: `P0.x` = pre-launch scaffolding (auth, shell, design tokens, Supabase clients — done). `P1.x` = goals (life areas, goal CRUD/lifecycle, participants, milestones, tasks, schedule variance, per-goal mini timeline — done). `P2.x` = money (pots, cashflow items, FX rates, the ledger, pledges/allocation, budget variance, and the money dashboard at `/money` — done). `P3.x` = the full cross-goal timeline at `/timeline` (multi-zoom scale, windowed data, collision stacking, lanes, desktop/mobile layouts, overlays, navigation, a performance pass — done; requirements pre-specified in `PHASE-3-REQUIREMENTS.MD`, see Architecture). `P4.x` = check-in and RAG (the weekly check-in flow at `/check-in`, RAG colour/scoring surfaced across the app, per-goal overrides, momentum/divergence, capacity suggestions at `/settings/capacity`, and wiring the llama message system to real events — done). `P5.x` = critical-path scheduling (CPM-aware task scheduling and dependency editing on the goal detail page, critical-path highlighting and dependency arrows on `/timeline`, slip preview, the constellation archive at `/constellations`, the annual retrospective at `/retrospective/[year]`, and a v1-hardening pass — data export, error boundaries, loading/empty states, a Supabase-call error-handling audit, and a mobile pass — done). `P6.x` = bucket list, trips, and the map (P6.0's Unsplash integration, P6.1's someday list at `/someday`, P6.2's Mapbox integration, P6.3's trip management at `/trips`, P6.4's trip route map plus the `/map` overview, P6.5's trip stops on the cross-goal timeline, and P6.6's llama copy pass — done). `P7.x` = profile, avatars, and achievements (P7.0's avatar library integration, P7.1's avatar editor at `/profile/avatar`, P7.2's achievement evaluation wiring, P7.3's profile pages at `/profile` and `/profile/[handle]`, P7.4's achievement copy pass and five new achievements, and P7.5's v1-shipping pass — done). No unbuilt stub pages remain.

## Stack

Next.js 16 (App Router) + TypeScript, Supabase (Postgres + Auth + RLS), Tailwind CSS v4, shadcn/ui (`radix-nova` style), deployed on Vercel.

Unit tests (Vitest) are colocated as `*.test.ts` next to the module they cover (e.g. `src/lib/money.test.ts`, `src/lib/timeline/scale.test.ts`, `src/app/(app)/goals/goal-transitions.test.ts`) — run a single file with `npx vitest run path/to/file.test.ts`. `vitest.config.mts` runs everything under `environment: "node"`: pure-logic tests only, no React component tests yet (no `jsdom`/`@testing-library/react` installed — add them per the Next.js Vitest guide in `node_modules/next/dist/docs/` if/when component tests show up). **`npm test` runs in CI** (`ci.yml`'s `ci` job, added P10.0 — the navigation-manifest route-coverage test needed something to actually enforce it on every PR) — a green PR does mean the suite passed, but it's still worth running locally while iterating rather than waiting on a push. Correctness for SQL (schema, triggers, RLS) is checked separately by running the `supabase/local/*` scripts against a scratch Postgres — see "Database" below. There's also no Storybook; UI states meant for visual review live at `/styleguide` and `/styleguide/llamas` (real routes in the running app, not a separate tool).

CI (`.github/workflows/ci.yml`, runs on every PR) has two jobs. `ci` does, in order: `npx next typegen` (needed so `tsc` can see route-generated types like `LayoutProps`/`PageProps`), `tsc --noEmit`, `npm run lint`, `npm test` (P10.0), `npm run build`. `db-isolation` (P9.0) replays every migration against a clean Postgres 17 instance, then runs every `supabase/local/*` suite — see the Database section below. Both are gates only — Vercel's own GitHub integration builds and deploys independently of them, so CI passing/failing doesn't control whether a deploy happens.

To run a single non-test check rather than the whole CI sequence, run that one command above directly — there's no per-file filtering for lint/build.

## Non-negotiable rules

1. All monetary values are integers in minor units (cents/pence) with an explicit 3-letter currency code alongside. Never floats, never a bare number. Format for display only at the render boundary.
2. Never query Supabase from client components with the service role key. All privileged operations go through Next.js route handlers or server actions.
3. Row Level Security is the security boundary. Never disable it, never bypass it with the service role to "make a query work". If a query returns nothing, the policy is the thing to inspect.
4. Dates are stored UTC (`timestamptz`) or as a bare `date` where time of day is meaningless. Display in the user's timezone from `profiles.timezone`.
5. Task dates are derived from `offset_days` + `duration_days`, never entered directly.
6. Database types are generated from the schema, never hand-written. Regenerate after any migration.
7. No `localStorage` or `sessionStorage` for application data.

## Architecture

**Route groups.** `src/app/(auth)/` (login, signup, onboarding — reachable while unauthenticated) and `src/app/(app)/` (dashboard, timeline, goals, trips, money, check-in, profile — gated). The split is enforced in code, not just by folder naming: `src/lib/supabase/middleware.ts` (invoked from `src/proxy.ts`, see Gotchas) redirects based on auth state and whether a `profiles` row exists yet, using explicit `AUTH_ROUTES`/`UNGATED_ROUTES` allow-lists rather than inferring from the route group.

**Four Supabase client constructors, not one** — pick the one matching where the code runs, don't share instances across requests:

- `src/lib/supabase/client.ts` — browser/Client Components, anon key.
- `src/lib/supabase/server.ts` — Server Components/route handlers/Server Actions, cookie-based session, created fresh per request.
- `src/lib/supabase/middleware.ts` — the proxy/middleware layer specifically; the one place session-cookie writes are guaranteed to succeed (Server Components can't write cookies at all — `server.ts`'s `setAll` silently no-ops there by design).
- `src/lib/supabase/service.ts` (P4.6) — server-only, service-role key, bypasses RLS entirely. Not the "query returns nothing, bypass RLS to make it work" move rule 3 forbids: it exists narrowly for tables with no user-facing INSERT policy _by design_ (e.g. `llama_messages` — users can `SELECT`/`UPDATE` their own rows but have no way to `INSERT` one, because messages are system-authored). If a query against a table the user is meant to write to comes back empty, the policy is still the thing to inspect, not this client. Current call sites: `src/lib/llamas/emit.ts`, `src/app/api/fx/refresh/route.ts`, and `src/app/(app)/money/fx/actions.ts`.

**Server action conventions** (`src/app/(app)/goals/`, mirrored under `src/app/(app)/money/`). Goal, task, milestone, and participant mutations each live in their own `"use server"` file (`actions.ts`, `[id]/tasks-actions.ts`, `[id]/milestones-actions.ts`, `[id]/participants-actions.ts`); money's pots, cashflow, FX, and ledger each get their own `actions.ts` the same way. All of them share a `ActionResult<T> = { ok: true; data: T } | { ok: false; error: string }` return shape rather than throwing. Two things repeat across all of them, deliberately:

- A local `getUserId(supabase)` helper calls `auth.getClaims()` and `redirect("/login")` on a missing session — every action runs from an already-gated `(app)` route, so a missing session here means it expired mid-use, not a first visit.
- Whether an extra `owner_id`/`goal_id` filter gets layered on top of a query is a conscious per-table decision, documented inline at each `getUserId`: it's added where RLS alone is broader than what the UI should allow, and skipped where the RLS policy (e.g. `tasks_write`/`milestones_write` as `app.can_edit_goal(goal_id)`) already is the exact authorization surface wanted. Don't add a filter "for safety" without checking which case applies — an unnecessary one can silently exclude collaborator-owned rows.

The goal lifecycle graph itself lives in `[goals/]goal-transitions.ts`, split out from `actions.ts` purely because a `"use server"` file may only export async functions — `ALLOWED_GOAL_TRANSITIONS` and `transitionLabel` need to be imported as plain values by both the server action and client-rendered buttons. Follow the same split for any future enum-driven state machine (task/milestone status, trip status, etc.).

**The llama message system** (`src/lib/llamas/`) is the app's copy/notification layer: two personas, Derek (blunt, handles red/amber/overdue/over-budget) and Fluffy (warm, handles green/completions/streaks/first-use). `types.ts` defines the `TriggerCode` union and per-trigger params; `registry.ts` maps each trigger to a speaker + priority (the speaker is decided once, centrally — call sites never pick a llama); `copy.ts` holds enumerable copy variants per trigger, viewable side-by-side at `/styleguide/llamas`. Adding a new triggered message means touching all three files. Every trigger carries **at least three copy variants**, picked at random by `getLlamaCopy` (P6.6 brief, verbatim: "two isn't enough once you're using the app daily — repetition is what makes a character feel like a robot") — checked by reading each one aloud against the two-sentence character brief at the top of `copy.ts`'s Derek/Fluffy blocks, not just by counting array entries.

**Wiring the llamas to real events (P4.6, `src/lib/llamas/emit.ts` + `evaluate.ts`).** `emitLlamaMessage` is the one write path — it looks up speaker/priority from the registry, renders body via `copy.ts`'s `getLlamaCopy`, and inserts through the service-role client (`llama_messages` has no user-facing INSERT policy; see the Supabase clients list above), then lets the DB-level `app.filter_llama_message` trigger drop the row if the user's `llama_frequency` mutes it — `emitLlamaMessage` never duplicates that muting logic itself. `evaluate.ts`'s `evaluateLlamaTriggers(supabase, userId)` runs every wired trigger for one user, debounced to at most once an hour via `profiles.llama_evaluated_at` (0020) — claimed _before_ the checks run so two near-simultaneous calls don't both do a full pass (advisory feature, small acceptable race window, not worth a lock). It's called from two places: `check-in/actions.ts`'s `submitCheckIn` (after the check-in's own RAG-snapshot trigger, so `goal_red`/`goal_amber`/`goal_green`/`goal_improved` see the fresh snapshot) and a dashboard load. Two dedupe strategies, matched to the trigger's shape: level-triggered conditions that stay true continuously (`goal_undefined`, `task_overdue`, `budget_exceeded`, `checkin_due`, `checkin_streak`, `capacity_exceeded`) use `hasUndismissedMessage` — skip while an undismissed message for the same (trigger, resource) exists, free to refire once dismissed; edge-triggered conditions (the four `goal_*` status-change triggers, compared across each goal's two most recent `rag_snapshots`) use `hasReportedSince` — skip if any message of that trigger family was created at or after the snapshot being compared, regardless of dismissed state. `goal_completed`/`trip_completed` are deliberately _not_ evaluated here even though they're wired triggers — both are emitted inline, exactly once, at the moment `transitionGoalState` completes a goal (`goals/actions.ts`, branching on `kind` between the two — a trip-kind completion gets `trip_completed` instead of `goal_completed`, never both), which is strictly more precise than detecting it by polling. P6.6 added three more evaluators, same `hasUndismissedMessage` dedupe family as the level-triggered ones above: `trip_booked` (every stop _and_ leg on an active trip is `booked`/`done`; a trip with neither yet is excluded — vacuously "booked" isn't locked in), `trip_over_budget` (`v_trip_estimates.total_estimate_minor`, not `v_goal_funding`'s ledger spend — the stops-and-legs-aware sibling of `budget_exceeded`), and `stop_unbooked_soon` (a stop within 30 days still at `booking_state: 'idea'`, deduped per-stop). P6.6 also added three first-use messages — "a first-run line from each llama... the difference between software and a present" (brief, verbatim) — `first_goal` (finally wired; the trigger existed since P0.6 with no real emit site until now), `first_trip`, and `first_budget_set` (Derek's, since target amounts are already his territory): all three are naturally idempotent (a fresh count of exactly 1 can only ever be true once) and emitted inline from `createGoal`/`createTripGoal`, not polled — see those functions' own comments.

**Money's dashboard is view-heavy, not computed in application code.** `/money` (`src/app/(app)/money/page.tsx`) and its sub-pages read from Postgres views — `v_allocation_summary`, `v_pot_balances`, `v_goal_funding`, `v_goal_affordability` — rather than joining and aggregating client-side; `src/lib/budget-variance.ts` and `src/lib/money.ts` only handle the pure display-side math (variance calc, minor-units formatting). If a money number looks wrong, check the view definition (`Schema.MD` / the migration) before suspecting the TypeScript. `v_goal_affordability` covers `save_toward` goals only — `spend_against` goals don't have an affordable-from date, per `006 affordability test`.

**Database.** `Schema.MD` is the narrative source of truth for the data model (24 tables, RLS design, RAG scoring rules, FX handling, what's built vs. not-yet-wired) — read it before touching anything schema-adjacent, it explains _why_ the shape is what it is, not just what it is. It was written as a complete upfront design doc in the very first commit and describes the full intended schema, phases ahead of the code that would eventually build it — that's why later migrations (0014 onward) keep finding it already an accurate description of what they're adding, rather than needing an update themselves. `supabase/migrations/` is still catching up to the live schema and isn't a complete, replayable log — as of this writing it holds `0009_monthly_cashflow_breakdown.sql`, `0011_timeline_items_view.sql`, `0012_financial_horizon.sql`, `0014_checkin_engine.sql` through `0021_critical_path_scheduler.sql` (check-in engine, its public surface, the goal-RAG view, override history, rating trend, capacity suggestions, llama-evaluation debounce, the critical-path scheduler). Its numbering is deliberately not gapless — `0010` and `0013` are both unclaimed (see PHASE-3-REQUIREMENTS.MD's R2 for `0010`; `0014`'s own header notes `0013` the same way) — so check the live schema/`database.ts` rather than the highest committed filename when picking the next number. `src/types/database.ts` is already generated against the real schema (regenerated and reformatted after 0012, confirmed against a real `supabase gen types` run, not hand-written — rule 6 intact), so trust that file for current table/column shapes even where migration SQL is absent. Worth remembering regardless: this session had a near-miss where an uncommitted regen (added after 0011, never committed) got silently reverted by an unrelated `git checkout` used to undo a _different_ failed regen attempt — everything from P3.1 onward ran on that uncommitted file without anyone noticing until a later `tsc` run broke. **Commit `database.ts` in the same change as the migration that required it**, not later; an uncommitted regenerate-after-migration is one `git checkout` away from silently reverting to the last committed schema shape. `supabase/local/*` are numbered psql scripts (`000 auth shim` through `008 critical path test` — auth shim, smoke test, RLS isolation test, schedule test, life areas test, timezone test, affordability test, check-in test, critical path test) for validating schema changes against a throwaway local Postgres before they touch the real project — see the "Running it locally" section of `Schema.MD` for the exact sequence. Several of the 0014+ migrations (0014, 0016, 0018, 0021) document objects that were already live on the real Supabase project before the migration file existed — verified against a real `supabase db dump`, not hand-derived — rather than introducing new behaviour; their own headers say so, worth checking before assuming a migration file is the origin of something vs. a transcription of it.

**Timeline math (`src/lib/timeline/`).** `scale.ts` wraps `d3-scale`'s `scaleTime` into an orientation-agnostic `TimelineScale` (`toPixel`/`toPixelSpan`/`ticks`) that only ever returns numbers — it has no opinion on `left`/`width` vs. `top`/`height`, or on layout at all. P3.0 extended it with a second, zoom-aware constructor, `createScale(zoom, anchorDate, rangePx)`: the domain is derived from `ZoomLevel` (day/week/month/quarter/year) and centred on `anchorDate` rather than fit to a data extent — at day zoom a multi-year extent is unrenderable. `widthForItem` is a thin, duck-typed wrapper (`{ toPixel(date): number }`) shared by both scale shapes, so call sites reach for rendered pixel width instead of branching on `duration_days` (R1). `stack.ts` (P1.11) does interval-stacking for the per-goal mini timeline; `stacking.ts` (P3.2) is the full-timeline sibling — same "minimum meeting rooms" greedy idea but a distinct implementation, not a shared one, because its placement order is `starts_on`/`sort_order`/`item_id` (a calendar-date sort, per R4), a different axis from `stack.ts`'s sort-by-pixel-start. Its `assignSubRows` folds each item's estimated label width into its effective pixel footprint (labels collide before bars do), reserves a single sub-row for milestones (never stacked among themselves, never interleaved with bars), and excludes goals entirely (they're a background band, not a competing bar — rendered separately in P3.4's `HorizontalTimeline`). `lanes.ts` (P3.3) splits a set of items into life-area/owner/goal lanes — also `Date`-free (bare ISO date strings sort correctly as strings, so there's no reason to touch `Date` until a lane's items reach `assignSubRows`). `item-status.ts` (P3.4) derives a four-way completed/overdue/in_progress/not_started classification from `is_complete` + dates + a caller-supplied `today` — deliberately _not_ from each item's own richer status enum, following `goal-timeline.tsx`'s existing precedent of deciding "overdue" from dates rather than the enum (this was originally _also_ because that richer status "isn't available this far down," `v_timeline_items.status` having been designed to carry the parent goal's state uniformly instead — P6.5 found that had silently stopped being true, see the `goal_status` note below; `classifyItemStatus` itself didn't need to change, since it never actually depended on the assumption, but the comment justifying it did). P6.5 added `isBeyondFinancialHorizon` alongside it — a stop's `starts_on` past `app.financial_horizon()`'s cutoff, the same bare-date lexicographic comparison `lanes.ts` already leans on. `overlays.ts` (P3.6) is the last pure piece, and genuinely shared _rendering-adjacent_ logic rather than layout: `computeOverlayLine` positions a single-point-in-time guideline (today marker, financial horizon) against any scale, and `needsStickyLabel`/`needsTruncatedLabel` encode R1's width-vs-viewport decision — both orientations call the same functions, just feeding them width or height depending which axis time runs on there. All of this is shared between P1.11's per-goal mini timeline (`src/components/timeline/goal-timeline.tsx`) and the full cross-goal timeline (Phase 3) — keep layout/component concerns out of this directory; it stays plain-`Date`-(or bare-date-string)-in/numbers-or-lanes-out. `PHASE-3-REQUIREMENTS.MD` (binding, derived from a since-deleted spike whose findings are preserved in `SPIKE-NOTES.md`) specifies the constraints that timeline work must satisfy: sticky labels keyed off rendered pixel width not duration, a single timezone-derived `today` computed once per request, bars anchored at their start (not centered), pixel-space (not date-space) collision stacking, range-windowed queries rather than list virtualization, and shared scale/separate-per-orientation layout constants. Read it before touching anything under `timeline/`. `PERF-NOTES.md` (P3.8) has the performance baseline this all needs to hold to — real numbers on stacking cost and scroll container size, a by-hand trace of the query-debounce/cache behaviour, and `src/lib/timeline/perf.test.ts`'s realistic 240-item dataset is the one to rerun and diff against before/after any change here, not a fresh ad hoc one. `PERF-BUDGET.md` is the living target/ceiling reference PERF-NOTES.md's own numbers get checked against — targets were fixed before any measuring happened (per its own header, a budget written after measuring is just a description of what you built), P3.8 and Phase 5's critical-path scheduler have each filled in their rows, and it carries a dated Log table for every pass after that; several rows (timeline first paint/re-render/frame rate, cache hit rate, the critical-path overlay render) are still genuinely open because they need a real browser/device or a UI that doesn't exist yet — check there before assuming a number, rather than re-deriving one.

**Horizontal timeline layout (`src/components/timeline/horizontal-timeline.tsx`, P3.4/P3.6, desktop/≥768px).** One `overflow-auto` container, `position: sticky` doing the pinning independently per axis (`top` for the date axis row, `left` for the lane-label gutter column, both for the corner cell) — not multiple scroll containers with JS-mirrored `scrollLeft`/`scrollTop`. Nothing between the sticky elements and that single scrolling ancestor may carry `overflow-hidden`/`overflow-clip` (R1) — that's the literal bug that broke the P0.8 spike's band labels on scroll, so it's worth checking first if a sticky element here ever stops sticking. Bars anchor at `starts_on` and are never centred (R3); milestones are the one deliberate exception, centred on their date as diamonds. Owns its own layout constants (gutter width, bar height, axis height, lane padding) — deliberately not exported and not shared with `vertical-timeline.tsx`. P3.6 added the today-marker/financial-horizon overlay (`OverlayLines`, spanning every lane via CSS Grid's `grid-row: 1 / -1` rather than computing total content height in JS) and per-item labels (`ItemLabel`): `position: sticky` is applied to a bar/band's label unconditionally, since it's inert until the item is actually wider than the viewport — the `needsStickyLabel` decision only gates a cosmetic backdrop chip, not correctness, which matters because there's no real viewport measurement wired up here (`ASSUMED_VIEWPORT_PX` is a documented guess, not a `ResizeObserver` reading).

**Vertical timeline layout (`src/components/timeline/vertical-timeline.tsx`, P3.5/P3.6, mobile/<768px).** A second, separate component — no `orientation` prop threaded through the horizontal one, per R6 and both packages' briefs. Same single-`overflow-auto`-plus-sticky-children structure as the horizontal layout, but transposed: time runs top to bottom, the date axis is a fixed-`left` rail (not a fixed-`top` row), and lanes stack as vertical collapsible sections instead of horizontal rows — `TimelineView`'s existing mobile single-expand state (P3.3) drives which one lane is open. The genuinely interesting bit is what carries over from `assignSubRows` unchanged: its sub-row numbers become _horizontal_ offsets here (an overlapping item sits to its right, not below it), so it's lane _width_, not height, that depth drives — the exact same function, reinterpreted onto the other axis, which is what R6 means by "the date maths transfers cleanly but the layout constants do not." Own layout constants again (rail width, column width, column gap) — not shared with `horizontal-timeline.tsx`, and the 4-way status-colour mapping is independently re-declared here too rather than imported, same colocation reasoning as `goal-timeline.tsx`'s `taskFill`/`milestoneFill`. `TimelineView` now owns zoom _and_ pan itself (it didn't before P3.5) specifically so it can default zoom to week on mobile / month on desktop and keep tracking that default — for as long as the user hasn't picked a zoom manually — as the breakpoint changes. P3.6's overlay lines run _horizontally_ here (`top: px`) instead of vertically, and only ever render inside whichever one lane is expanded — with only one lane's body ever in the DOM on mobile, "across all lanes" already means "within the expanded one." P3.7's `onHoverItem`/`onNavigate` split (hover/focus previews, click navigates to `/goals/[id]`) is identical in both orientation components — an interaction-semantics decision, not layout, so it isn't something R6 says to keep separate.

**Navigation and interaction (P3.7).** `TimelineView` now also owns hover/focus state (`hoveredItemId`, repurposed from what used to be click-selection — click navigates now, per the brief's explicit "no drag, no resize, no inline editing here; editing happens on the goal detail page"), a `useRouter().push("/goals/[id]")` navigate handler, and a keyboard-shortcut effect (`+`/`=`/`-`, guarded against firing while an input/textarea/select/contenteditable has focus). Zoom never touches `anchor` — only `zoom` — so "zooming preserves the centre date" holds by construction, not by any special-cased recovery logic; `scale.test.ts` has a dedicated test for exactly the year-to-day case P3.7's acceptance criterion names. The hover card (`item-hover-card.tsx`) renders as a fixed corner panel keyed off `hoveredItemId`, not a cursor-following tooltip — schedule variance on it is optional and caller-supplied (`scheduleVariances` prop, a `Map<goalId, pp>`) for the same reason `ownerNames`/`goalTitles` already are: `v_timeline_items` doesn't carry what `computeScheduleVariance` needs. The two empty states are told apart by a second, unwindowed existence check (`hasAnyGoalsEver`, a one-off `goals` count query, deliberately separate from the windowed/filtered hook) — `displayItems.length === 0` alone can't distinguish "no data" from "filtered/windowed to nothing."

**Timeline lane components (`src/components/timeline/`, P3.3).** `TimelineView` is the stateful container the brief calls for — grouping mode, filters, per-lane collapse state, and selection all live here as plain `useState`, never `localStorage`. Desktop and mobile collapse state are two _separate_ pieces of state (`desktopCollapsedLaneIds` vs. a single `mobileExpandedLaneId`), not one derived from the other — that's deliberate: switching to mobile never touches the desktop set, so switching back restores it untouched, which is what makes surviving the breakpoint switch (R6) true without extra bookkeeping. `TimelineLanes` underneath is purely presentational (given `Lane[]`, render them); neither component is ever remounted or `key`ed by grouping mode or breakpoint, since that's exactly what would reset scroll position. `timeline-item-adapter.ts` bridges `v_timeline_items`'s all-nullable generated row type (Postgres reports every view column nullable, regardless of the underlying tables' real constraints) into the non-null shapes `lanes.ts`/`stacking.ts` expect, dropping any row missing a required field rather than crashing. `useIsMobile` (`src/hooks/use-is-mobile.ts`) is `useSyncExternalStore` used the way the P0.8 spike notes say it should have been the first time (R2) — subscribed to `matchMedia`'s actually-stable `matches` value, not a continuously-changing clock, with a fixed `false` server snapshot to avoid a hydration mismatch. One non-obvious data fact worth knowing before touching life-area grouping: "Uncategorised" is a real, system-seeded `life_areas` row (`is_system: true`, own `id`/`colour`/`sort_order`) that `goal-form.tsx` already defaults every goal into — not a `null`-`life_area_id` sentinel. `lanes.ts` still handles a genuinely null/unmatched `life_area_id` (a synthetic fallback lane, shown only when it has items), but that path is a defensive edge case, not the common one.

**Timeline data layer (`src/hooks/use-timeline-items.ts`, P3.1).** The first (and so far only) client-side Supabase query in the app — everything else goes through server actions/server components, but a scroll-driven data layer has to live on the client. Queries `v_timeline_items` (0011's view — unions goals/milestones/tasks, plus trip stops as of P6.5, see below) windowed to the visible range plus a ~1-viewport buffer (R5), debounced ~150ms, and cached by (filters, buffered window) so scrolling back to an already-fetched window is a cache hit. The "active goals only" filter reads `goal_status` (0025, P6.5) — the parent goal's state, present uniformly on every row specifically for this filter; `status` itself is each item's own status (goal state / milestone open-or-completed / task status / trip stop booking state), which used to _also_ double as the filter column until it silently stopped being goal-state-shaped for anything but goal rows (see the `goal_status` paragraph below for the full story — this is the fix, not a P3.1-era design). `src/app/(app)/timeline/debug-items/` is a dev-only (`notFound()` in production) harness that dumps its output as JSON — same convention as `/styleguide`, but inside `(app)` because it needs a real session for RLS. This is data-fetching only; no rendering built on it yet.

**Trip stops on the timeline (P6.5, migration `0025_timeline_items_goal_status.sql`).** `v_timeline_items` already had a fourth branch, `item_type = 'trip_stop'` (`starts_on`/`ends_on` from `computed_arrival`/`computed_departure`, `is_point` from `nights = 0`, `status` from `booking_state`) — live before this package, wired into rendering by it. Building this surfaced a real bug rather than something the package itself introduces: `status` was designed (0011) to carry the _parent goal's_ state uniformly, specifically so the timeline's default "active goals only" filter (`use-timeline-items.ts`'s `.eq("status", goalState)`) would work the same way across every item type. Confirmed against the live view (a scratch `supabase db dump`, not assumed) that this had stopped being true well before trip stops were added — the milestone branch returns `'completed'`/`'open'`, the task branch returns `tasks.status`, neither of which is ever the literal string `'active'` — so the default filter was silently returning _zero_ milestones or tasks, goal rows only, confirmed by a direct count against live data before writing the fix. `0025` adds `goal_status` (the goal's state, uniform on every row, appended as the last column — `CREATE OR REPLACE VIEW` can only add columns) as what the filter should read instead; `status` keeps its current (correct, just newly _useful_) live behavior of being each item's own status, which trip-stop rendering genuinely needs (`bookingStateFillClass` in `horizontal-timeline.tsx`/`vertical-timeline.tsx`, independently re-declared in each per that file's existing convention) in a way tasks/milestones never did before. Trip stops get their own shape — a pill (bar) or circle (`is_point`, zero-night stop), never a task's rectangle or a milestone's diamond — "distinct visual treatment... this is travel, not work" (brief, verbatim); colour is purple at increasing opacity for idea/researching/booked and the `--star` token for done, deliberately not the RAG palette (same "don't collide with an existing meaning" rule P5.1's critical-path outline already follows). Stacking needed no new logic (brief, verbatim): `stacking.ts`'s `assignSubRows` just treats `trip_stop` as another bar-stacking candidate alongside `task`, sharing the same greedy pass. A stop whose `starts_on` is past `app.financial_horizon()`'s cutoff (`isBeyondFinancialHorizon`, `item-status.ts`) gets a dashed outline on the bar (visually aspirational) and a plain-language row on `item-hover-card.tsx` ("Beyond your financial horizon") — the visual and the words are two different acceptance-criterion halves, not redundant with each other.

**Check-in and RAG (P4.0-P4.4, `src/app/(app)/check-in/`, `src/lib/rag.ts`, `src/lib/rating-trend.ts`).** The scoring itself is a database function, `app.compute_goal_rag` (pre-existing, predates every migration this repo captures) — not application code, so a wrong-looking RAG number means checking that function/`v_goal_rag` before suspecting the TypeScript, same principle as the money dashboard's views. Weekly check-in periods are a 7-day window ending on `profiles.check_in_day`, derived by `app.current_checkin_period` off `app.today_for_user()` rather than raw UTC `current_date` (0014) — the same timezone fix PHASE-3-REQUIREMENTS.MD's R2 established one level up. `check-in/actions.ts`'s `saveGoalRating`/`saveCapacityRating`/`saveOverallNote` autosave as you go (upserting on `(check_in_id, goal_id, user_id)` so repeat taps overwrite rather than duplicate); `submitCheckIn` is the deliberate, separate act that flips `submitted_at`, firing a DB trigger that snapshots RAG for every rated goal and clears any stale override — and is one of the two call sites that invoke `evaluateLlamaTriggers` (see the llama-wiring paragraph above). `src/lib/rag.ts` is display-only logic over `v_goal_rag`'s row — `ragInputs()` reads its loosely-typed `inputs` jsonb defensively (every key optional, since which keys are set depends on which branch of `compute_goal_rag` produced the row); `isGracePeriod`/`isUndefinedGoal` distinguish "goal under 14 days old, colour not earned yet" from "no tasks and no budget, grey means undefined" — both render as no-colour states in the UI, not a warning. `hasScheduleMomentumMismatch` flags schedule-green/momentum-red specifically (worst-wins already collapses that into a plain red `overall_status` with no explanation), and the three `describe*Dimension` functions build the "22% behind — 4 of 12 tasks done, 61% elapsed"-style sentences from the view's own numbers, never re-deriving them (`schedule-variance.ts`'s own top comment already flags its JS transcription as something that can drift from the DB's authority — `rag.ts` sources from the live view instead). `rating-trend.ts` (P4.4) builds the sparkline series and the divergence sentence from `v_goal_rating_trend` (0018): the shared x-axis is the 12 most recent _calendar_ periods any participant rated in, not each participant's own most recent 12, so two people missing different weeks still align; `describeDivergence` states each participant's rating and stops ("You rated this 5, Sophia rated it 2.") — deliberately not sorting or highlighting who's "lower," per the brief's "a prompt to talk, never a verdict." Per-goal overrides (P4.3, `goals/[id]/override-actions.ts`) write straight to the goal's override columns via `goals_update`'s ordinary RLS — no override-specific authorization layer — and never touch either existing expiry mechanism (the check-in-submit trigger's stale-override clear, `app.effective_goal_rag`'s expiry check); a history trigger (0017) logs every override write automatically, so the action itself never writes to `rag_override_history`.

**Capacity suggestions (P4.5, `src/app/(app)/settings/capacity/`).** `app.suggest_goal_limit_change` (DB-side) proposes raising or lowering `profiles.active_goal_limit` and supplies its own Derek/Fluffy-toned reason text, rendered directly rather than re-templated through the llama copy layer. Raising is one tap (Fluffy); lowering (Derek) always means picking a specific active goal to move to `someday`/`archived` in the same action — never just decrementing the number and leaving the user over their new limit. Dismissing a suggestion doesn't change what the DB function computes, only whether this page shows it again this period (fire-and-forget — a failed dismiss just means the same true suggestion reappears next load). `capacity_exceeded` (one of the wired llama triggers above) checks `count >= limit` — P1.7's original inequality, deliberately not `v_user_capacity.over_limit`'s stricter `>`.

**Critical-path scheduling and dependency editing (P5.0, migration `0021_critical_path_scheduler.sql` + `goals/[id]/dependency-actions.ts` + `task-dependencies-editor.tsx`).** `task_dependencies` existed since P1 but was deliberately left unwired until now — "setting predecessors with no arrows to see and no float to compute is data entry with no payoff" — so this is the package that finally makes it worth using. `app.recompute_goal_schedule` branches on `app.goal_has_dependencies`: a goal with zero dependencies still gets the cheap offset-only path (`computed_start`/`computed_end` from `start_date + offset_days`, no float, `is_critical` always false) that `tasks_derive_dates`'s pre-existing BEFORE trigger already wrote; only a goal that actually has a dependency network pays for the full CPM pass, run as an AFTER trigger (`tasks_recompute_network` on task changes, `task_dependencies_recompute` on dependency changes) that overwrites the BEFORE trigger's simple values. CPM itself is a fixed-point relaxation over a temp table (forward pass for earliest start/finish, then backward for latest start/finish from the projected end), not a topological sort — deliberate, since `task_dependencies` already rejects cycles at write time (`prevent_dependency_cycle`), so the graph is guaranteed a DAG and iterating to a fixed point needs no separate ordering step; iteration is capped at `2 * task_count + 10` purely as a termination guarantee. `total_float_days`/`is_critical` land on `tasks` itself; `v_critical_path` (`security_invoker`, RLS follows the underlying `tasks` row exactly) is the read surface for "every task currently on the critical path, across any goal." On the UI side, `dependency-actions.ts`'s `addDependency`/`updateDependency`/`removeDependency` enforce same-goal-on-both-sides and no-duplicate-edge server-side (the schema doesn't reject either) and always return the goal's full tasks _and_ dependencies read back fresh — a dependency change ripples via trigger to `computed_start`/`computed_end`/`total_float_days`/`is_critical` on tasks the caller never touched, so an optimistic single-row patch would be wrong here, unlike every other mutation on the goal detail page (which do use `onSaved` single-row patches). `task-dependencies-editor.tsx` keeps the common case (finish-to-start, zero lag) to one select + one click, with dependency type/lag behind each edge's own "Change" toggle. `humanizeDbError` (`src/lib/errors.ts`) special-cases `prevent_dependency_cycle`'s error text (a `RAISE EXCEPTION` naming both task ids, not a named constraint `CONSTRAINT_NAME_RE` could match) into "That would create a circular dependency" — cycle detection itself stays entirely the trigger's job, this only translates the message.

**Unsplash integration (P6.0, `src/lib/unsplash/`).** Split into an isomorphic `types.ts` (the trimmed `UnsplashPhotoResult` shape, `withUnsplashUtmParams`/`UNSPLASH_HOME_URL` — safe to import from a Client Component) and a server-only `server.ts` (the only place `UNSPLASH_ACCESS_KEY` is read or `fetch` hits `api.unsplash.com`), mirroring the `client.ts`/`server.ts` split the Supabase clients already use for the same reason: nothing that touches the key is reachable from browser code. `/api/unsplash/search` and `/api/unsplash/download` are thin route handlers over that module, gated on any signed-in session (same bar as `/api/fx/refresh`'s in-app path — not admin-only, but not anonymous, since an unauthenticated caller shouldn't be able to spend the shared quota). Unsplash's API terms shape the implementation directly: photos are hotlinked from their CDN and never downloaded to our own storage (`someday_items`/`trip_stops` already carry `unsplash_photo_id`/`unsplash_thumb_url`/`unsplash_full_url`, predating this package per Schema.MD's usual "written ahead of the code" pattern, and a check constraint already rejects a photo id without author attribution — confirmed live by `supabase/local/001 smoke test`); the download-tracking endpoint at a result's own `links.download_location` fires from `<PhotoPicker>` at _selection_, not display, and only after validating the URL actually points at `api.unsplash.com` (a client-supplied string reaching a server-side `fetch`, so this is a cheap SSRF guard, not something Unsplash itself requires); attribution links carry `utm_source=starmap&utm_medium=referral`, matching what the smoke-test fixture already hand-writes into `unsplash_author_url`. Caching is two-layered against the 50-requests/hour demo-tier cap: `server.ts` keeps a module-scope, best-effort TTL cache (helps for real on a single warm instance, not guaranteed across cold starts or concurrent instances), while `<PhotoPicker>`'s own per-mount client cache is what actually protects normal use (backspacing to an already-searched query is a cache hit, no network call) — same debounce-then-cache-check-through-one-`setTimeout` shape as `use-critical-path-edges.ts`. `<PhotoPicker>` and `<UnsplashAttribution>` are the reusable pieces; nothing wires them into `someday_items`/`trip_stops` persistence yet — that's P6.1's job. `trips/debug-unsplash/` is a dev-only harness (same `notFound()`-in-production convention as `/styleguide`, inside `(app)` because the routes need a real session, same reasoning as `timeline/debug-items`).

**The someday list (P6.1, `/someday`).** `someday_items` is a free-standing, per-user wishlist table — no `goal_id`, not scoped to any goal the way tasks/milestones are — with its own independent share-grant surface (`app.has_grant('someday_item', id, ...)` on `someday_select`/`someday_update`) that this package doesn't build UI for, since nothing in the brief asks for it. `src/lib/someday.ts` holds the pure, unit-tested pieces — `filterSomedayItems`/`sortSomedayItems` (cost sorts on raw minor units with no currency conversion, a documented simplification, not this app's usual rate-stamped FX path) and `isSomedayMilestone`, which `someday/actions.ts`'s `createSomedayItem` checks against a fresh post-insert count to fire the `someday_milestone` llama trigger — same "exactly once, at the moment, not polled for" shape as `goal_completed` (see the llama-wiring paragraph above), not one of `evaluate.ts`'s debounced sweeps. Place fields (`place_name`/`latitude`/`longitude`/`country_code`/`mapbox_place_id`) are entered by hand in `someday-form-dialog.tsx` — a deliberate stub ahead of P6.2's real Mapbox Geocoding client, per the P6.1 brief. Progress ("total, promoted, still dreaming, and distinct countries wanted") reads straight off `v_someday_progress` (grouped by `user_id`; a user with zero items has no row at all, so `page.tsx` substitutes an all-zero row rather than leaving the UI to handle `null`), the same "never recompute what a view already computed" rule the money dashboard follows. Promotion itself — `app.promote_someday_to_stop`, confirmed live against the real schema (copies name/place/cost/unsplash fields onto a new `trip_stops` row, links it back via `someday_item_id`, stamps `promoted_at`, never deletes the original) — has no `public` wrapper yet and isn't called from this package; `/someday` only _displays_ already-promoted items (via a three-hop `trip_stops` → `trips` → `goals.title` chase in `page.tsx`, since a trip's title lives on its parent goal, not on `trips` itself) and blocks deleting them client- and server-side. The action to promote a place into a trip belongs to P6.2/P6.3, once `/trips` exists to promote into.

**Mapbox integration (P6.2, `src/lib/mapbox/`, `src/components/mapbox/`).** Same isomorphic-`types.ts`/server-only-`server.ts` split as P6.0's Unsplash integration, and the same reason: nothing that reads `MAPBOX_SECRET_TOKEN` (`/api/geocode`'s forward-geocoding proxy) is reachable from browser code. The _other_ token, `NEXT_PUBLIC_MAPBOX_TOKEN`, is genuinely meant to be client-side — Mapbox's own design, not an exception to rule 2 (that rule is about the Supabase service-role key specifically) — read directly by `<PlaceMap>` to render the map itself; restrict it by URL in the Mapbox dashboard rather than treating it as a secret (see DEPLOYMENT.md's Mapbox section, including the "no hard spending cap, set a billing alert" note). `<PlaceMap>` (`place-map.tsx`) never imports `mapbox-gl` at module scope — it's loaded via a runtime `import()` inside a mount effect, so the library's own ~200KB+ is a separate webpack chunk fetched only once a map actually mounts; every call site additionally wraps it through `lazy-place-map.tsx`'s `next/dynamic(..., { ssr: false })`, which also keeps `<PlaceMap>`'s own (small) component code out of any route that never renders a map, and sidesteps SSR for a component whose effects touch `window` the moment they run. `<PlacePicker>` is the search-and-pick half — same debounce-then-cache-through-one-`setTimeout` shape as `<PhotoPicker>` (P6.0) and `use-critical-path-edges.ts`, 400ms per the brief — and composes `<PlaceMap>` for its own single-marker preview once something's selected. `someday-form-dialog.tsx` (P6.1) is the first real caller: place name and country stay plain, always-editable text fields (not gated on Mapbox being configured at all), while `<PlacePicker>` only owns setting/clearing the coordinate pin — the same graceful-degradation shape as that dialog's photo section when Unsplash isn't configured, so an item is always fully saveable either way.

**Trip management (P6.3, `src/app/(app)/trips/`, migration `0024_trip_creation.sql`).** "A trip is a goal with kind = 'trip' plus a trips row" (brief, verbatim) — it inherits budget, RAG, participants and timeline placement rather than reimplementing any of them, so `/trips/[id]` deliberately doesn't rebuild the goal-editing UI at all; it links out to `/goals/[id]` ("View as goal") for anything that isn't stops/legs/estimates, and `goal-form.tsx` now refuses to let "Trip" be _picked_ as a kind (no option in create mode, disabled once a goal already is one) — a trip-kind goal with no matching `trips` row is an orphan the rest of this package doesn't defend against. `app.create_trip_goal` (SECURITY DEFINER) inserts both rows in one transaction — "creates the goal and the trip together" (brief) can't mean a client-driven multi-statement transaction, since PostgREST gives one statement per request, so atomicity has to live inside the function, same reasoning P5.2's `preview_task_slip` comment gives for its own in-function rollback. `app.reorder_trip_stop` and `app.promote_someday_to_stop` both predate this migration (confirmed live via `supabase db dump`, not assumed — Schema.MD's usual "written ahead of the code" pattern) but neither had a `public.*` wrapper yet, so neither was actually reachable from `supabase.rpc()` until now.

Every stop and leg mutation in `stop-actions.ts`/`leg-actions.ts` — not only reordering — returns a fresh `{ stops, legs }` pair fetched straight from the database, and `trip-detail.tsx` always replaces both wholesale rather than patching one row: `trip_stops_recompute`'s AFTER trigger can silently ripple `computed_arrival`/`computed_departure` onto every _later_ stop from a single nights edit, insert, or delete, and deleting a stop cascades to any leg pointing at it (a soft delete, so `trip_legs`' real `ON DELETE CASCADE` foreign keys never fire — `deleteStop` does that cleanup itself). This is the brief's "do not renumber client-side... refetch after" instruction generalized to every mutation that could ripple, not only `app.reorder_trip_stop`'s own park-then-renumber algorithm — the same "never reimplement the derivation in TypeScript" instinct P5.2 established for CPM. `stops-section.tsx`'s drag-and-drop (`@dnd-kit`, same library `life-area-manager.tsx` uses) is the one place in this app where a drop deliberately does _not_ apply an optimistic local reorder — it dims the list until the server's real order arrives instead.

`<PlacePickerField>` (`src/components/mapbox/`) is the "pin on map, optional" shape factored out once P6.3 needed it a second and third time (trip origin, stop location) beyond `someday-form-dialog.tsx`'s original P6.1 copy — same picked/unpicked branching, same `<PhotoPicker>`-style "current value + Change" affordance once something's picked.

**Trip map and the `/map` overview (P6.4, `src/components/mapbox/place-map.tsx`, `src/app/(app)/map/`, `src/lib/map-overview.ts`).** `<PlaceMap>` grew up from P6.2's single-preview-marker component into the shared engine both this package's views need: `PlaceMapMarker.sequenceNumber` swaps the default teardrop pin for a custom numbered-circle DOM element (mapbox-gl's own `color` option only ever draws the teardrop), `PlaceMapMarker.onClick` is attached to `marker.getElement()` regardless of which shape that element is, and `PlaceMapLine` replaced the older `connectLines: boolean` prop (never actually exercised by any real caller before this package) with explicit per-segment lines — the trip map needs one line per _leg_, styled solid or dashed by that leg's own `mode`, not one continuous polyline auto-drawn through every marker in array order. No drag-to-reorder was ever added to the map itself — "reorder from the map by dragging markers in the sequence list beside it, not by dragging on the map itself" (brief: fiddly on a phone, ambiguous with panning) — `stop-map.tsx` is purely a read view keyed off the same `stops` prop `stops-section.tsx`'s existing `@dnd-kit` list already reorders; a drop's `reorderStop` round trip re-renders both from the same fresh server state, no special wiring between them.

`/map`'s "dreams in one colour, planned stops in another, visited in the star token" (brief, verbatim) is a colour-only signal by itself — same "never colour alone" instinct as the RAG badges (P4.2) — so `map-overview.tsx` pairs every dot with a legend row and repeats the kind as text in the click card. `src/lib/map-overview.ts`'s `buildOverviewPlaces` is the one place that decides "visited": a trip stop's own `booking_state === 'done'`, not the parent trip's goal state — one trip can have some stops done and others still an idea, and that's a real distinction worth keeping at stop granularity rather than collapsing to "the whole trip is complete or it isn't." `cancelled` stops are dropped entirely (not a dream, not planned, not visited — nothing's happening there); items with no coordinates can't appear on a map at all and are filtered both in the page's own query and defensively inside `buildOverviewPlaces` itself.

**Achievements and avatars (P7, migrations `0026_achievements_avatars.sql` + `0027_avatar_preset_assets.sql`, `src/lib/avatar/`, `src/components/avatar.tsx`).** Same situation 0014/0016/0018/0021 were each already in: `achievements`, `avatar_presets`, `user_achievements`, `profiles.avatar`, and their RLS policies pre-date any migration file (Schema.MD's usual "written ahead of the code" pattern — already reflected in `database.ts`); `app.evaluate_achievements`/`app.grant_achievement`/`app.presets_unlocked_by`, `v_available_presets`, and the `validate_avatar`/`enforce_pin_limit` triggers were _also_ already live by the time P7 started, so `0026` documents them (verified via `pg_get_functiondef`/`pg_get_viewdef`/`pg_get_triggerdef` against the real project, cross-checked against `supabase/local/010 achievements test`) rather than introducing them — the brief that opened this phase named it `0017_achievements_avatars.sql`, a number 0017_rag_override_history.sql already claimed by the time this phase started, so it's filed as 0026 instead (numbering isn't gapless in this repo — check the live schema, not the highest filename, per the Database section below). `evaluate_achievements`/`grant_achievement`/`presets_unlocked_by` live in the `app` schema with no `public.*` wrapper yet (same unreachable-from-`supabase.rpc()` situation P6.3's `reorder_trip_stop`/`promote_someday_to_stop` were in before that package added theirs) — wiring achievement evaluation to real events is a later P7 package's job, not P7.0's; `v_available_presets` is a plain `public` view and needs no wrapper.

`app.validate_avatar()` is what makes the unlock system non-decorative: a BEFORE trigger on `profiles.avatar` that refuses an unknown slot, an unknown/wrong-category preset code, or a real-but-locked one — enforced in the database, so equipping a locked outfit is never just a crafted API call away regardless of what client code does.

P7.0 picked **Avataaars** (`@dicebear/core`/`@dicebear/collection`/`@dicebear/avataaars`, pinned to `9.4.3` throughout — `@dicebear/collection` never published a release compatible with `@dicebear/core`'s current 10.x major, so 9.4.3 is the newest mutually-compatible pair across all three, not an arbitrary older pick) over Open Peeps, the brief's own first suggestion for the `pose` slot's "expressive posture options." That description doesn't hold for the installed version: Open Peeps 9.4.3's real `Options` type (checked directly, not from memory — collection options change between majors, per the brief's own warning) has no body/posture concept at all, just a bust portrait like Avataaars. Avataaars won instead because it has something Open Peeps genuinely doesn't: a `clothing` option with 9 real distinct garment shapes, mapping one-for-one onto 9 outfit presets. `pose` became an expression instead, via the `eyes` option — the brief's own sanctioned fallback for exactly this situation, just needed for both collections rather than one. `backdrop` and `accessory` have no native Avataaars equivalent either (a flat `backgroundColor`, and eyewear-only `accessories`) and get the same brief-sanctioned fallback extended one slot further: hand-drawn SVG layers (`src/lib/avatar/render.ts`) rather than a library option.

`avatar_presets.asset_ref` (0027) stores only the shape-defining option value per preset — bare hex for `skinColor`, the real `clothing`/`eyes` string, or a custom-layer treatment name for backdrop/accessory — never a colour recolour, which lives in `src/lib/avatar/presets.ts` instead, keyed by preset `code` and hand-synced with `asset_ref` (same "small enum colocated in code, independently re-declared" convention `taskFill`/`bookingStateFillClass` already follow, chosen for the same reason: avatars render in lists and need to be fast and synchronous, not wait on a table read for something that only changes when a migration does). Recolouring exists to make avatars read as part of the night-sky theme rather than a third-party widget — skin tones are the one deliberate exception, kept naturalistic rather than tinted purple. One thing only verified by actually rendering and looking, not by reasoning about it: `outfit_formal`'s first colour choice (a near-black matching the palette's own darkest token) was functionally invisible against the default backdrop, and `outfit_stargazer`'s `graphicShirt` came back wearing a random bat logo because Avataaars picks its own `clothingGraphic` when one isn't pinned — both are why every `clothesColor` in `presets.ts` deliberately avoids the palette's near-background darks, and why `clothingGraphic` is always explicit. `<Avatar avatar={...} size={...} />` takes `profiles.avatar` straight off a Supabase row (no cast needed — `parseAvatarSelection` narrows the generic `Json` type defensively, same posture `rag.ts`'s `ragInputs()` already takes with its own loosely-typed jsonb) and needs no hooks/`"use client"`, so it renders from a Server Component; the actually-expensive step (DiceBear's own SVG generation) is memoised at module scope inside `render.ts` keyed by the base/outfit/pose combination, not per component instance — many identical avatars across a whole session share one cached render, which is the form of memoisation "avatars appear in lists" actually calls for. `/styleguide/avatars` (same dev-only, `notFound()`-in-production convention as `/styleguide/llamas`) renders every preset in every slot for visual review.

**The avatar editor (P7.1, `/profile/avatar`).** `page.tsx` fetches `v_available_presets` once, grouped by category into `presetsBySlot`, and passes it to `avatar-editor.tsx` (`"use client"`, the interactive half — same server-component-fetches/client-component-owns-state split `settings/capacity` already uses). "Show locked presets, don't hide them... hidden unlocks motivate nothing" (brief) means every tile renders regardless of `is_unlocked`; a locked one is greyed (`opacity-45 grayscale`), carries a small lock badge, and its `unlock_hint` — the unlocking achievement's own `description`, already joined in by the view — surfaces two ways: a native `title` for hover, and a `Popover` for tap, since this app has no dedicated Tooltip component and building one wasn't this package's job. The brief's real point is stronger than "show a disabled control": a locked tile has **no `onSelect` wired to it at all** — clicking it can only ever open the popover, never write a code into `selection` — so the database's `insufficient_privilege`/`check_violation` split from `app.validate_avatar()` (0026) exists purely as defense in depth for a stale client or a direct API call, not a path normal use reaches (`errors.ts` maps both anyway, since "a user hitting a database error for something the UI let them click is a bug in the UI" cuts both ways — the mapping should exist even if nothing should ever trigger it). Every preset tile previews against the user's _current_ in-progress selection (`{...selection, [slot]: preset.code}`), not held constant against a default like `/styleguide/avatars` does — the point here is "how would this look on mine," not an isolated catalogue. `accessory` gets one synthetic tile no `avatar_presets` row backs (`NONE_ACCESSORY`, always unlocked) since it's the one slot `DEFAULT_AVATAR` deliberately leaves unset — every other slot always has a value, so there's nothing to opt out of. "Randomise... picking randomly from unlocked options only" (brief) iterates every slot independently and, for `accessory` specifically, leaves it unset on a fresh account rather than forcing a pick — neither `accessory_compass` nor `accessory_telescope` is ever free, so "unlocked options" is genuinely empty there until an achievement fires. The pinned-preview-over-scrolling-options mobile layout (brief: usable at 390px) is one `sticky top-0` block, not a second scroll container — the app shell's `<main>` has no `overflow-auto` of its own (P3.4's sticky-label rule, R1, applies one level up here too), so `top: 0` really does mean the browser viewport, no JS scroll-tracking needed.

**Achievement evaluation (P7.2, migration `0028_achievement_evaluation.sql`, `src/lib/achievements/`, `src/components/achievement-celebration.tsx`).** `app.evaluate_achievements`/`app.grant_achievement`/`app.presets_unlocked_by` (0026) had no `public.*` wrapper either — same situation `reorder_trip_stop`/`promote_someday_to_stop` were in before P6.3's 0024 — so 0028 adds one for each, every one pinning `auth.uid()` internally rather than accepting a caller-supplied user id (matching `public.current_checkin_period`'s own shape, not `create_trip_goal`'s), plus `profiles.achievements_evaluated_at` for the one call site that's a genuine poll.

Five trigger sites, only one of them debounced: `evaluateAchievements` (the core, always runs) is called directly from check-in submit, goal/trip completion (the same `transitionGoalState` branch covers both — a trip-kind completion is not a second call), and ledger entry creation (`createLedgerEntry` specifically, not `updateLedgerEntry`'s own internal insert-then-delete-old, which shares the same low-level `insertEntry` helper but isn't a "creation" the way the brief means it). Only dashboard load goes through `evaluateAchievementsDebounced`, an hourly-debounced wrapper keyed off `achievements_evaluated_at` — a deliberately separate column from `llama_evaluated_at` (0020), since these are two independent systems and sharing one timestamp would let one silently suppress the other for the same hour. `honest_reckoning` (trigger_type `capacity_honesty` — the brief's own name for it, but _not_ its `code`, confirmed live after a first pass that conflated the two and silently granted nothing) is the one achievement `app.evaluate_achievements` never computes; it's granted explicitly from `settings/capacity/actions.ts`'s `lowerLimitByMovingGoal` via `grantAchievementManually`, the moment a "lower" capacity suggestion is actually accepted — "an act of judgement, not an accumulation" (brief), and idempotent the same way every other grant path here is.

Every one of those five call sites returns a `NewlyUnlockedAchievement[]` (code, name, and `presets_unlocked_by`'s own rows) as part of its `ActionResult`, built by `evaluate.ts`'s shared `celebrate()` helper — which also fires `achievement_unlocked` (a new Fluffy trigger, priority 1, same tier as `goal_completed`) through the ordinary `emitLlamaMessage` path, so "Fluffy delivers the news by name" is durable and inbox-visible regardless of whether the live celebration below ever renders. `<AchievementCelebration>` is that live half — a small fixed-position card per newly-unlocked achievement, shown by whichever client component just received a non-empty array, linking straight to `/profile/avatar`. "Never celebrate twice" needs no dedupe state anywhere in this stack: `app.evaluate_achievements`/`app.grant_achievement` are both idempotent, so a given code can only ever appear in a _newly_-unlocked array once, ever, on the one call that actually earned it — every render downstream of that is a genuine first-time unlock, and the mobile-friendly pattern of _not_ tracking "have I shown this" client-side just falls out of that guarantee for free. The two animations (`.achievement-celebration-card`'s pop-in, `.achievement-star`'s pulse) follow `globals.css`'s existing `.constellation-star` shape exactly — a dedicated class plus a scoped `@media (prefers-reduced-motion: reduce)` override — rather than Tailwind's `motion-safe:` variant, which nothing else in this app uses yet.

**Profile pages (P7.3, `/profile`, `/profile/[handle]`).** No new migration — everything this package needed was already live: `user_achievements_select`'s RLS (`user_id = auth.uid() OR app.has_grant('profile', user_id, 'view')`, pre-existing since 0026) already does the hard half of "another user's profile, viewable when they've shared a goal with you or granted profile access," and `profiles_select`'s own RLS is broad enough (any signed-in user, any non-deleted row) that the profile row itself was never the thing gating this page to begin with. `[handle]/page.tsx` checks two independent, explicitly-queried conditions — a real `profile`-scoped `share_grants` row, or a shared goal computed via the two-query in-memory join CLAUDE.md's Server action conventions section documents (my goals via `goals_select`'s own RLS, then which of those the profile owner also participates in via `goal_participants_select`'s RLS, which permits reading every participant row on a goal I can already view, not just my own) — and renders nothing at all if neither holds, an application-level gate layered on top of that permissive row-level read, not something RLS itself enforces. All of this was verified against the real database directly (a scratch second profile, a shared goal, a grant, inserted and rolled back in one transaction) rather than reasoned about from the policy text alone: confirmed a stranger can read the bare profile row but never `user_achievements`, and that a grant is what flips pinned-achievement visibility, nothing else. "Nothing about their money, their private goals, or their check-ins" holds by construction — this page never queries any of it, not by filtering results down after the fact.

The achievement grid itself only ever appears on `/profile` (own) — `achievement-grid.tsx`, a full 9-card grid (`achievements` is a small, non-user-scoped catalogue, freely readable) with locked cards showing their own `description` as the unlock hint (achievements have no separate `unlock_hint` field the way `v_available_presets` does; the description already reads as one). Pinning follows the exact same "prevent client-side, map the trigger's error as backstop" shape P7.1's avatar editor established for `app.validate_avatar()`: a fourth pin never reaches `toggleAchievementPin` at all (the count is checked client-side first), and `app.enforce_pin_limit`'s `check_violation` is mapped through `humanizeDbError` regardless, per the same "the mapping should exist even if nothing should ever trigger it" reasoning. `<PinnedFlair>` (`src/components/pinned-flair.tsx`) is the up-to-three display used by _both_ pages — pure, no interactivity, since pinning itself only ever happens from the grid.

`<Avatar>` (P7.0) picked up an actual `React.memo` in this package, on top of the module-scope SVG cache it already had — two complementary layers now, not one: the cache saves regenerating the same preset combination twice anywhere in the app, the memo saves a client-rendered list (participants, task owners) from re-parsing an unchanged avatar's SVG into the DOM when a sibling re-renders. Wired into `participants-section.tsx` (each name is now also a link to `/profile/[handle]` — the only real discovery path into that route anywhere in the app) and `task-row.tsx`'s owner badge, replacing its old text-initials placeholder. Check-in ratings and the divergence sentence (`momentum-section.tsx`) were left unwired — the divergence display is prose ("You rated this 5, Sophia rated it 2"), not a name list, and turning it into one would be a bigger redesign than "add an avatar next to an existing name."

**Achievement copy (P7.4, migration `0029_achievement_copy_and_new_achievements.sql`).** All nine original `code`s are untouched (name/description-only rewrites, navigation/night-sky themed throughout — True North, Polaris, Dead Reckoning, Course Correction), except two `trigger_config` thresholds that moved: `southern_cross` 20→10 goals and `well_travelled` 10→3 countries, per the brief's own "earnable by two people planning a move, not permanently greyed clutter" bar. Five new achievements (`first_landfall`, `star_chart`, `fair_wind`, `twin_stars`, `full_orbit`) each get a real `app.evaluate_achievements` CASE branch, not an app-code "manual" grant — `manual` stays reserved for `honest_reckoning` alone, the one genuine act-of-judgement case. `full_orbit`'s `checkin_tenure` counts _total_ submitted check-ins (45 of 52), deliberately not `checkin_streak`'s live unbroken-streak logic — forgiving of missed weeks on purpose, so "a year of the app" doesn't require literal perfection the way `long_haul`'s half-year streak does. Two of the five unlock new avatar presets (`pose_serene`/`closed` eyes for `full_orbit`, the hand-drawn `accessory_twin_stars` badge for `twin_stars`); the other three are flair alone, per the brief's own "every achievement need not unlock something." Each achievement also gets one hand-written Fluffy line (`ACHIEVEMENT_UNLOCK_LINES` in `copy.ts`) — a flat map keyed by achievement code, not the usual three-random-variants shape, since an achievement only ever unlocks once per user ever (P7.2's idempotency guarantee already established this), so there's nothing to keep fresh through repetition the way a daily-use trigger needs. `emitLlamaMessage` grew an optional `bodyOverride` param (P7.4) so `celebrate()` can supply this specific line instead of `getLlamaCopy`'s random pick — same "some copy is already exactly right at the source" reasoning `suggest_goal_limit_change`'s reason text already established (P4.5).

**The v1-shipping pass (P7.5, migration `0030_seed_achievements_and_presets.sql`).** "Run all suites against a fresh database" surfaced two real gaps neither `tsc`/lint/tests/build nor the live project itself could ever catch, precisely because the live project was never actually _fresh_: `010 achievements test` referenced a goal id (`...002`) nothing ever seeded — a plain typo, `...001` is the real fixture — and, more seriously, `achievements`'/`avatar_presets`' original seed rows (nine achievements, twenty-one presets) had never been captured by any committed migration at all, only ever inserted directly into production (the same "written ahead of the code" pattern Schema.MD documents for schema, but this time for data). 0026 created the tables and assumed the rows existed; 0027 updated them; 0029 originally assumed the same. Fixed two ways: 0029's nine `update`s became an `insert ... on conflict do update` (correct whether the row already exists or not), and 0030 backfills the twenty-one original `avatar_presets` rows with their real, current `asset_ref` values — deliberately not the pre-0027 placeholders, since 0027 (numbered earlier) has already run and won't run again by the time 0030 does on a fresh replay. All ten `supabase/local/*` suites pass end-to-end against a genuine from-scratch database as a result (schema replayed from a live `pg_dump --schema-only`, not the incomplete `migrations/` directory alone — see the Database section below).

The Supabase-call audit (P5.5's own, re-run here against everything P6/P7 added since) found the identical bug class recurring in five newer files — a `.single()`/`.maybeSingle()` result read without checking `error`, silently producing a wrong default (a mislabelled currency, a real failure indistinguishable from a genuine 404) instead of surfacing. Fixed the same way AppLayout's own instance was fixed in P5.5: throw on a real error in page-level fetches (`retrospective/page.tsx`, `money/page.tsx`, `money/ledger/page.tsx`, `trips/[id]/page.tsx`'s `trip`/`goal` fetches), log-and-degrade for the one non-critical helper where throwing would break a server action's own `ActionResult` contract instead (`money/ledger/actions.ts`'s `getUserContext`, whose fallback only ever reaches an error message string, never the actual ledger write). Also found `<AchievementCelebration>`'s dismiss button had copy-pasted `LlamaMessage`'s _pre_-P5.5-fix button shape (a 24×24 tap target from bare `p-1` padding) rather than its current one — added the same `max-md:size-11` treatment — and that the component's own `fixed bottom-4` positioning sat inside the mobile `TabBar`'s occupied strip rather than clearing it, fixed to match `<main>`'s own `pb-[calc(5rem+...)]` compensation value.

Error boundaries, `/api/export`'s RLS-and-ownership scoping, and the signed-out-redirect gate (`proxy.ts`'s allowlist-everything-else-is-gated shape, which needed zero changes to already cover every route P6/P7 added) were all confirmed already correct from P5.5 — nothing to fix, checked directly rather than assumed.

**Deployment** is documented in `DEPLOYMENT.md`: no `vercel.json` (defaults are correct), the three required env vars and why `SUPABASE_SERVICE_ROLE_KEY` must never gain a `NEXT_PUBLIC_` prefix, Supabase Auth redirect allow-list config, and the migration-then-regenerate-types workflow.
